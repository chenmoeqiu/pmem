# DESIGN —— 为什么这么做

> 这份文件回答"为什么是这个设计"，不回答"现在做到哪一步"（那是 [`HANDOVER.md`](HANDOVER.md)）。
>
> 每条决策固定四段：**结论 / 理由 / 被否决的方案 / 怎么验收**。缺一段的那条不算决策，只是偏好。
>
> 适用范围：`pmem 0.1.0` · schema **v15** · 零第三方依赖。
> **本文的事实以代码为准**：版本号与 schema 号在 `pmem/__init__.py`，行为在 `pmem/*.py`。
> 文字与代码不一致时，改文字——这条纪律来自一次真实事故：文档比代码早写二十分钟，
> 于是留下了一条"已经实现了却写着没实现"的遗留项，后来差点被照着重做一遍。
>
> 除第 1 节那个已经脱敏的起源故事外，真实数据与真实例子**不在本文，也不在本仓库**：
> 它们留在各自使用者的机器上（真实的数据库、真实的对话记录）。
> 本文只给一般化的结论；示例数据见 `samples/`，全部是合成的。
>
> 术语：**「作者」** 指这个记忆库的所有者（第 1 节故事的主角）；**「用户」** 指使用者
> ——个人部署里两者是同一个人，写成两个词只是为了分清「故事里的人」与「接口里那个人」。

## 1. 问题与红线

**结论**

目标不是"记住更多"，而是**不乱联想**。为此愿意牺牲召回率，换精确与可追溯。
数据形态是本地、纯文本、带时间戳、人可读、随时可迁移。

四条不可动的约束——前三条是内容约束，第四条是程序约束：

1. **禁止向量检索**（不是"暂时不用"）
2. **原文全量保存**，不用摘要替代原文
3. **每条消息必须有时间戳**，精度诚实标注；`unknown` 的时间必须是 `NULL`
4. **时间戳由存储层盖章**，调用方无权传入"现在几点"

**理由**

这个项目起源于一次失败，值得完整记下来——因为它的失败方式很具体：

> 作者让 AI 帮忙规划一次**徒步**。它建议"带上你那台 ZV-E10"，以及"晚上喝一杯威士忌"。
> 作者并没有买那台相机；而徒步也不该背玻璃瓶。

问题不是它不懂作者，是它把"旅行 = 放松 = 威士忌"这种东西在向量空间里缝了起来：
"风景"离"摄影"近，"摄影"离"相机"近，"旅行"离"放松"近，"放松"离"酒"近。
每一跳都合理，整条链是假的。它不知道那台相机到底买没买，也不知道徒步背玻璃瓶意味着什么——
**它不是没有知识，是知识之间没有事实边界。**

这就是"更懂你"和"不乱联想"的分歧点。前者优化"作者看到结果时的惊喜感"，
后者优化"作者能不能相信每一条结论的出处"。选择后者意味着接受一个难看的事实：
**没有指名的东西，召回不到。**

第 2 条红线容易被误解。保留原文 + 时间轴，目的不是"能复述当时的原话"，
而是为了回答**"我对这件事是什么态度、为什么、还会不会变"**。
一条偏好其实是四样东西：断言 + 理由 + 时间 + 边界条件。蒸馏只留下断言，
另外三样全丢——所以"蒸成任何一句话都错"：说"喜欢"错，说"不喜欢"也错。

第 3、4 条是同一件事的两半：**精度诚实**与**盖章权**。
让模型"顺便推断一个时间"是最省事也最脏的做法——推断出来的时间和真实时间
在库里长得一模一样，之后无法区分，也只能一直错下去。

**被否决的方案**

- 用摘要/条目替代原文：省空间、省 token、看起来更"像记忆"，但它把可追溯性一次性销毁了。
- 让运行时或模型自己决定时间：会出现"导出时刻冒充发生时刻"，时间轴倒挂。
- 把时间戳做成可选字段（缺了就补当前时间）：等于用错误数据掩盖缺失数据。

**怎么验收**

红线不许靠自觉，得靠代码。这四条各有守卫：

| 红线 | 守卫 |
|---|---|
| 禁向量 | 代码里**没有向量这条路径**（不是开关关着）；检索只有检索层的两条 |
| 原文全量 | `messages.content` 只追加；派生层任何写入都不改原文 |
| 时间诚实 | `verify` 第 6 项：`unknown` 却有时间的 = 0，`message` 却无时间的 = 0 |
| 存储层盖章 | `note` 的 `--created-at` 直接 argparse 报错（exit=2），`smoke_ports` 有断言 |

## 2. 为什么禁向量

**结论**

检索只有两条路：**标签**（主路径）与**原文精确匹配**（兜底）。不做语义相似度召回，
不做混合检索，不做向量重排。这不是配置项，是结构性选择——库里没有向量，也就没有
"悄悄打开"的开关。

**理由**

1. **语义近邻不等于事实成立**。向量空间里"一次远行"离"摄影"近，"摄影"离"某台相机"近，
   于是推理链自己长了出来。中间每一跳都"合理"，结论却可能整条是假的。
2. **向量回答得了"像什么"，回答不了"有没有发生"**。"准备买"和"已经清仓"在向量空间里
   距离极近，但对记忆来说这是两个相反的事实。区分它们靠的不是相似度，是时间轴。
3. **不可读、不可审计**。浮点向量无法人工检查"为什么召回了这条"。而本项目的要求是
   每条结论都能点回原话。
4. **不可迁移**。换一个嵌入模型，整个索引就得重建，历史判断随之漂移。

一条可复现的技术事实支撑了"字面路线可行"这个前提：SQLite 3.53.1 上实测，
FTS5 的 `trigram` 分词器对两字中文词（如"天气"）返回 **0 条**，`unicode61` 又把整句中文
当成一个 token。所以中文必须自己做预分词（见第 5 节），而预分词之后，
**字面匹配已经足够精确**——精确到这个场景不需要用近似来换召回。

> 诚实边界：这条实测只证明"字面能做到"，不证明"向量做不到"。禁向量的理由是
> 第 1–4 条（事实边界与可审计），不是"向量技术不行"。不要用实测去支撑一个价值判断。

**被否决的方案**

- 向量 + FTS 双路 RRF 融合（同类产品的主流做法）：融合权重本身就是个说不清的超参数，
  且会把"语义相近但事实无关"的东西重新抬回来。
- 仅向量、无 FTS：连型号、编号、人名都查不准。
- 向量只用来"重排"已有候选：看似安全，实际把不可解释的分数引入了最后一公里。

**怎么验收**

`verify` 第 2、3 项：中文精确子串必须命中（探针词随机抽自真实库），不存在的词必须返回 0 条。
两项一起才成立——只测"能查到"会漏掉"乱查到"。

## 3. 存储：只追加，一个例外

**结论**

- `conversations` / `messages` / `attachments` 三层是**原始层，只追加**。
- 附件按 **sha256 内容寻址**落盘，目录按日期分层，同一份内容只存一份。
- **`purge` 是唯一的破坏性操作**，一次穿透五层：原文 → FTS 索引 → 派生层 → 附件 → 审计。
- 审计只记"哪个 id 在何时被清除"，**绝不留内容**。
- 库文件在仓库内被误提交时，`check_git_safety` 直接拦下。

**理由**

原始层是所有推理的地基。地基允许改写，上面的每一条结论就都失去了参照物——
"他当时是不是这么说的"将无法回答。所以写入只做一件加事，不做减法。

内容寻址解决的是"同一张图被发过五次"这种现实：按消息 id 命名会存五份，
按内容寻址只存一份，且天然可去重、可校验（`verify` 抽查 sha256）。
重复导入必须幂等：同一条消息 + 同一个 sha 不新增附件行。

`purge` 之所以必须是"唯一"的破坏性操作，是因为 append-only 需要一个**显式的例外出口**，
否则用户想撤回某些内容时，唯一的选择是删库——那才是真正的破坏。
把它做成"唯一、显式、可审计、穿透所有副本"，缺一项都会留下残余：
只删原文不删 FTS，检索还能命中；只删行不删文件，磁盘上还在。

**被否决的方案**

- 附件按消息 id 命名：同一张图存多份，purge 时容易漏删副本。
- 物理删除行：破坏 append-only，且外键级联会静默带走派生数据。
- 只做软删（`state='deleted'` 保留内容）：那叫"看不见"，不叫"删掉"，撤回请求没被满足。
- 按目录整删：粒度太粗，会误伤同一条消息里的其他附件。

**怎么验收**

- `verify` 第 4 项：随机抽查 5 个附件，sha256 与文件内容不一致的必须为 0。
- `verify` 第 5 项：导出再读回，行数必须相等（导出往返）。
- `verify` 第 8 项：在临时库上 purge，断言索引 1→0、消息变 `purged`、附件变 `purged`、
  文件真的从磁盘消失、`purge_log` 恰好 1 条。
- `verify` 第 9 项：在仓库内伪造一个 `.db`，必须被 Git 安全防护拦下。
- `smoke_ports` 第 14–16 项：缺文件不阻断消息入库；同图不重复占空间。

## 4. 时间：盖章、分级、宁可没有

**结论**

- `created_at` 一律 **UTC ISO-8601**（毫秒）存储，展示时转本地偏移（默认 `+8`，固定小时数）。
- **四档精度**：`message` / `derived` / `conversation` / `unknown`。
- `time_precision = 'unknown'` 时，`created_at` **必须为 `NULL`**。
- 助手回复的时间是 `derived`：取它所回应的那条用户消息的时间。
- 调用方没有传时间的参数；"现在几点"由存储层取。

**理由**

时间是本项目的核心变量，不是附属字段。同一句话，在"上个月"和"现在"语境下答案相反，
所以每条消息必须能回答"它发生在何时"，而且要能回答"这个时间是猜的还是测的"。

把 `unknown` 强制设为 `NULL`，是为了让"不知道"在数据结构上就是空的。
如果允许一个占位值（比如 `1970-01-01` 或导入时刻），它会混进排序、混进热窗、
混进时间衰减，而且**再也没法把它挑出来**。宁可整列是空，也不要一个看起来像数据的谎。

助手回复用 `derived` 而不是"导出时刻"，是因为导出行为与对话行为不同步：
用导出时刻会让回复倒挂在提问之前，整条时间轴错位。

`+8` 写成固定配置而不是 `zoneinfo`，是零依赖的必然结果：Windows 上 `zoneinfo`
需要一个额外的 `tzdata` 包，那会破坏"零第三方依赖"。代价是夏令时地区不适用——
对一个本地个人记忆库，这个代价可以接受，且写在配置里可改。

**被否决的方案**

- 让模型顺便推断时间：推断值和真实值同形，之后无从区分。
- `unknown` 填占位时间：见上，比缺失更坏。
- 用系统时区做转换：同一份数据在两台机器上会显示成两个时间。
- 用导出/导入时刻当发生时刻：时间轴倒挂。

**怎么验收**

- `verify` 第 6 项：`unknown` 却有时间的 0 条；`message` 却无时间的 0 条。
- `smoke_ports`：`note --created-at` 必须失败（exit=2），盖章后的时间必须能被下一轮 `context`
  在热窗里看到（说明盖章值进了真实数据流，不是只在返回值里）。

## 5. 检索：双索引与"字面就行"

**结论**

- **两条索引**：标签（主路径）+ 原文 FTS（兜底）。
- 中文用**预分词索引列**：入库时在每个 CJK 字之间插空格，检索时走 phrase 查询。
- 多关键词 **OR 合并**，不 AND。
- 时间衰减在 **Python 侧**算（半衰期 180 天），SQL 只负责宽召回。
- 标签的 is-a（查父含子）用**物化路径前缀匹配**。
- 冷检索的排除**全部在 SQL 层**：当前会话、默认不调用的会话、已注入的热窗段。

**理由**

**为什么标签是主路径、全文是兜底。** 全文只认字面：用户说"那家做激光的公司"，
原文里可能一次都没出现过这个说法，只有具体名字——**词汇鸿沟**。
标签（从真实数据里长出来的闭集词表）把"换个说法还能不能查到"这件事补上了。
反过来，标签治不了型号、编号、金额、人名这些一次性字符串，那正是全文的主场。
两者不是"或"，是"主 + 兜"。

**为什么中文要预分词。** `unicode61` 把连续汉字当单 token（搜"天气"命中 0），
`trigram` 要求至少 3 个字符（两字中文词命中 0，见第 2 节实测）。
预分词把每个字变成一个 token，于是"连续 token 序列"就等于"原文的连续子串"——
用 FTS5 拿到了精确子串匹配，还保留了索引。关键约定只有一条：
**入库与检索必须走同一个 `text.tokenize()`**，否则索引和查询的形态对不上，静默返回空。

**为什么 OR 不 AND。** 多个关键词 AND 在一起，现实里很容易一条都不剩
（一句自然语言里抽出的四个词同时出现的消息，本来就少）。宁可召回宽一点，
让时间衰减和排序说话——反正后面还有证据门把关。

**为什么排除必须下推到 SQL。** 这是踩出来的：先取 top-8 再过滤，
当前会话会把名额占满，真实历史只剩 1 条。过滤动作发生在名额分配之后，
就等于**用错误的分母做筛选**。静音会话同理。

**为什么时间衰减在 Python 侧。** SQLite 的 `exp()` 依赖编译开关（`SQLITE_ENABLE_MATH_FUNCTIONS`），
在别人的机器上可能不存在。纯 Python 的指数衰减没有这个风险，且方便单测。
时间未知（`NULL`）的消息给中性权重 0.55，不惩罚也不奖励——不能因为"我不知道它什么时候说的"
就把它排到最后。

**为什么查父含子用物化路径。** `tags.path` 存 `维度/父/子` 这样的完整路径，
"国家的全部地点"就是一次 `path = ? OR path LIKE ? || '/%'`。不需要递归 CTE，
不需要手工维护子集表，也没有"改了父子关系忘了更新子集"的失配问题。
代价是：层级必须在**入库时**就写对（父级要先存在）。

**被否决的方案**

- trigram / unicode61 直接上：实测对中文基本无效。
- 关键词 AND：多词一条不剩。
- 取完再过滤（当前会话 / 静音 / 热窗）：名额被污染，见上。
- SQL `exp()` 做衰减：依赖编译开关。
- 扁平标签 + 手工维护子集表：维度会坍缩（见第 9 节）。
- 只维护一个"最近 N 小时"的时间窗：与热记忆边界脱钩，出现空洞（见第 8 节）。

**怎么验收**

- `verify` 第 2、3 项：命中与不命中，双向。
- `smoke_tag` 第 6 项：is-a 查父含子（父标签能带出子级）。
- `smoke_tag` 第 12、13 项：滑出热窗的段落必须可检索；标签必须真的接进对话链路
  （不是"能按标签查"，而是"对话时会用标签"）。
- 实机：`search --tag <父级>` 的命中数应显著大于 `--exact`（差值是子级贡献）。

## 6. 路由：要不要回忆，是一个独立决定

**结论**

路由是**独立的一步判定**，不让 agent 在生成时顺便决定。
判定结果四支：`casual`（闲聊）/ `work`（专业）/ 要回溯但有歧义 / 要回溯且有关键词。
三道关：**规则下限** → **模型判定** → **第三档复核**。

- 规则是**下限保护**，不是主判据：出现"上次/之前/记得"这类硬信号，模型说不用查也要查。
- 关键词必须**出自用户当前这句话**（忽略大小写、空格、连字符后比对），否则丢弃。
- 第一档判"不回溯"时触发**第三档复核**：用一次专门提问（"要回答这个，需要知道用户的个人处境吗"）
  再确认，改判则抬升 `need_recall`。
- 复核的触发条件是**结构性的**（"判了不回溯就复核"），不是词表。
- 对"当前这段输出"的改写/压缩/翻译请求，判为不回溯。

**理由**

**为什么独立判定。** 让同一个模型一边"想怎么回答"一边"决定要不要查历史"，
两件事会互相污染：需要查的时候它可能觉得"这个我能编"，不需要查的时候它可能顺手翻旧账。
独立判定还带来一个可审计的副产品：每次判定落 `routing_log`（含 `need_recall`、关键词、
理由、延迟、token），误查和漏查因此可以事后定位，而不是只能靠"感觉不对劲"。

**为什么规则只做下限。** 规则能覆盖你想得到的说法，覆盖不了换一种说法。
实测过一次词表式触发：在调优集上 100%，换留出样本只剩 **66.7%**——
"现在是不是买入机会""这个岗位适合我吗"这类句子一个词都不命中，但它们显然要个人处境。
所以规则只负责**绝不会错的那部分**（"上次""还记得"），其余交给模型 + 复核。

**为什么关键词必须出自原话。** 模型有一个很强的倾向：从"最近对话"里搬词。
一句"今天有点累"配上最近聊过的股票代码，就会去检索那只股票——这正是要避免的过度联想。
代码里做归一化比对，不在原话里的关键词直接丢弃；丢完一个不剩，就判歧义、转反问。

**为什么复核要结构性触发。** 这是"漏查"的主因：模型第一档判"不用查"里，
混着真正的闲聊和"隐性回溯"（问的是自己的处境，但句子里没有任何时间词）。
用词表去猜这类句子，就是上面那个 66.7%。改成"只要判了不回溯就再问一次"，
就把一个**语义问题**换成了一个**流程问题**——后者可以被穷举。

**被否决的方案**

- agent 自主决定要不要检索：对照组实测准确率 0.50，漏查 0.60、误查 0.25。
- 词表触发复核：留出样本 66.7%。
- 信任模型给出的关键词：会从最近对话搬词。
- 统一用"候选反问"处理歧义：会把无关闲聊也当候选（实测）。
- 规则当主判据：省一次调用，但漏查率不可控。

**怎么验收**

- `tools/eval_router.py`：三组样本（简单 / 硬样本 / 留出），A 组准确率 1.00、漏查 0.00、误查 0.00；
  B 组（agent 自主）0.50 / 0.60 / 0.25。
- `routing_log`：线上可看，`run.cmd log --last 20`，重点关注误查与漏查，而不是准确率均值。

> 诚实边界：三组样本一共 34 条，是自建的、带作者偏向；两组都没有给对话历史，
> 所以没测到 agent 在"信息更多的上下文里判断"这个理论优势。
> **能声称的是"独立路由在同等信息条件下不输、且错得可定位"，不能声称"更强"。**

## 7. 证据门：先判够不够，再决定说不说

**结论**

检索之后、作答之前，有一道**代码强制**的门。三条规则：

1. 声明"证据充足"却给不出任何 `used` 编号 → 判不足。
2. 声明"证据充足"但 `next` 不是 `answer` → 判不足。
3. `used` 里引用了本批次不存在的编号 → 剔除；剔空则判不足。

判不足时**默认先反问细节**（`clarify`），而不是只陈述"查到了但不够"。
只有门认可的那几条证据会交给生成器。

**理由**

没有门的时候，"命中 3 条但只够答一半"会被静默当成"有证据"，模型于是硬答。
这种错比"没找到"更难发现：输出通顺、引用了真实原话、结论却是拼的。

**为什么必须用代码，而不是在提示词里写"不够就说不够"。** 这条试过：模型倾向于
把话圆回来。它会把"我找到了一些相关信息"写成一个看起来像回答的段落。
所以三道校验全部落在 `gate.validate()` 里，模型的自我评估只是一个输入，不是结论。

第 2 条规则（`sufficient=true` 但 `next≠answer`）看起来多余，其实拦的是**自相矛盾的输出**：
这种情况下无论模型想干什么，都不该被当成"可以作答"。

**副作用是好的**：因为只把 `used` 里的证据交给生成器，所以不存在"召回 8 条只用 2 条"——
利用率是被结构保证的，而不是被提示的。

**为什么不足时要反问。** 用户明确表达过偏好：宁可他补一句"哪家公司、什么时间"，
也不要模型猜，更不要只丢一句"查到了但不够"。所以反问必须带上三样东西：
缺什么、按哪些关键词查的、下一次可以怎么补。只陈述不足等于把问题丢回给用户还不给线索。

**被否决的方案**

- 只在提示词里约束：模型会把话圆回来。
- 检索到就作答：幻觉的主要来源之一。
- 统一返回 `not_found`（只陈述不足、不追问）：用户明确否决。
- 先截断再过滤证据：名额被污染（见第 5 节）。

**怎么验收**

- `verify` 第 7 项：三个用例——空 `used` 判不足、越界 ref 判不足、正常引证放行。
- `smoke_tag` 第 18 项：用假 provider 强制判"不足"，断言返回 `clarify` 且追问里带缺失项。

## 8. 记忆分层：清醒段，以及不重不漏

**结论**

**热记忆 = 当前"清醒段"整段注入；冷记忆 = 其余，可检索。**

- "睡了一觉"的判据：**间隔 ≥ `sleep_gap_hours`（6）** 且 **这段间隔与睡眠窗口
  `sleep_window`（默认 01:00–08:00）重叠 ≥ `sleep_min_overlap_hours`（2 小时）**。
- 热记忆**整段注入不截断**（`hot_max_tokens = 0`）；真给了预算且装不下时，
  必须在注入文本开头**明说**丢了多少条，不允许静默丢弃。
- **注入边界 = 排除边界**：`segment_start_iso()` 一处计算，热窗注入与冷检索排除读同一个值。
- 检测到睡眠边界时，边界之前**还没打标**的会话入队 `cold_queue`（幂等），
  真正的切段 + 打标留到闲时批量做。
- 作息不规律时可用 `pmem sleep` 手动标一个睡眠点，**优先级高于自动推断**。

**理由**

热记忆之所以要"整段"，是因为它模拟的是人的短期记忆：聊到一半的话题不需要"检索"，
它本来就在脑子里。截断它就等于在对话中间制造失忆——而且是**静默**的失忆：
用户会以为系统记得，实际上最旧的几条已经被扔掉。

**为什么不是"跨自然日"。** 最初的规则是"跨天 AND 间隔"，实测在真实作息上失效：
- `22:03 → 次日 00:44`：跨了天，只隔 2.7 小时（其实没睡）→ 旧规则会误判为分段。
- `00:59 → 次日 12:33`：**没**跨天，隔了 11.5 小时（确实睡了一觉）→ 旧规则会误判为同一段，
  把前一天凌晨的消息一路带进今天中午的热记忆。

用户的原话是"熬夜的凌晨和起床后中午应该是要分段的"。睡眠窗口是比"自然日"更准的代理：
它描述的是"人大概在这段时间里不会说话"。两天规则合取（间隔够长 **且** 与窗口重叠够多）
才同时排除了上面两个反例。

**为什么注入与排除必须同源。** 这是本项目最贵的一个教训：两个地方各自计算边界，
哪怕差一分钟，就会出现一段"既没被注入、又被排除在检索之外"的消息——**永久黑洞**，
而且没有任何红灯。所以边界只算一次（`segment_start_iso()`），两个消费方读同一个值。

**为什么转冷之后必须自己整理。** 转冷的语义就是"这一段结束了，可以整理了"——
如果它只入队、等一个记得敲命令的人，那这个语义就只有一半：**记忆会一直停在"待整理"，
而没有任何东西告诉用户**。所以整理有三个入口：

1. **一轮对话结束**（助手那条写完）：顺手跑一点点（`cold.limit`，默认 2 场）。
   队列空时只是一次 SQL，几毫秒；有活儿时才花模型调用，而且回复已经发出去了。
2. **人工指令** `pmem daily`：强制或补跑。
3. **任何定时任务**：同一个 `daily.run`，幂等。

"闲时"由两个参数守住：`interval_hours`（默认 6，两次整理之间至少隔这么久）和
`limit`（一次最多几场）。攒了一周也只会在各轮里分批消化，不会一次爆掉。
失败的不标 `done_at`，留在队列里下次重试；离线/没有 key 时干脆不动队列——
**宁可不整理，也不能把会话标成"已整理"却没有标签**（那会永久失去打标机会）。

顺手的一个好处：整理通常落在"睡醒后的第一轮"，正是 API 的谷价时段。

**为什么热窗要标出"这条带了图"。** 模型收到的是文字：图存在库里，但它的内容不在提示词里。
如果不标注，用户发一句"看这张"加一张图，模型看到的只有"看这张"四个字，然后开始凭上下文猜
——这正是幻觉最典型的样子。所以带附件的消息渲染成
`（附图 N 张，已描述：… / 未描述）`；只要有未描述的图，开头还会明说
"你看不到图片内容，被问到时直接说看不到"。

这也解释了为什么描述要尽早写：**未描述的图对模型等于不存在**。
但"不存在"和"看不清"必须让模型分得清——前者它该说没有，后者它该说看不到。

**被否决的方案**

- "跨自然日"判据：上面两个反例。
- 固定 24 小时热窗：与真实作息无关，熬夜场景全错。
- 热记忆截断最旧的几条（静默）：制造失忆且不可感知。
- 注入与排除各自算边界：黑洞。
- 转冷同步做打标：一轮对话要额外等 N 次调用。
- 自动规则一刀切、不给手动出口：时差、白天补觉无法处理。

**怎么验收**

- `smoke_tag` 第 10 项：睡眠边界用例（含"没跨天但隔了 11.5 小时"这种反直觉输入）。
- `smoke_images` 第 7 项：热窗里带附件的消息要标出"附图 N 张（已描述/未描述）"，
  未描述时开头要说明"看不到，不要猜"。
- `smoke_tag` 第 11、12 项：滑出即可检索——热窗里的消息检索不到，滑出后必须能检索到，
  且**不能重复**出现。
- `smoke_tag` 第 14–16 项：转冷队列（边界触发、幂等、已打标的不再入队）。
- `smoke_ports`：盖章消息必须出现在下一轮热窗（热窗延续）。

## 9. 打标：闭集、挂在段上、从真实数据长出来

**结论**

- **六个闭集维度**：`主题 / 地点 / 人物 / 机构 / 任务 / 情绪`。值挂在维度下，
  `parent_id` + 物化路径表达 is-a。
- 标签挂在**话题段**（`segments(conversation_id, start_seq, end_seq)`）上，不挂在消息上；
  一段一套多维标签。**原文一条都不复制**，段只是区间引用。
- 打标单位是**会话**，不是单条消息。
- 只标用户消息；只写派生层；原文一个字不动。
- **闭集外**的值落 `pending`（待审），**不参与检索**；批准后立刻生效。
- 词表从**真实数据**里长出来，不靠拍脑袋列。
- **情绪只标用户自述的身心状态**，不标语气。

**理由**

**为什么多维而不是扁平。** 扁平标签会**维度坍缩**：地点、人物、主题抢同一层级，
最后必然出现"其他"这种垃圾抽屉。维度是闭集，等于先问"这是什么种类的东西"，
再问"是哪一个"——两个问题分开，坍缩就不会发生（实测：闭集外的候选约 4%，
绝大多数是模型给出词表外的新值或单字名）。

**为什么挂在段上。** 一场会话经常混多个话题：先问工具用法，再聊别的。挂在消息上太碎
（一条消息一个话题，上下文不够判），挂在会话上太粗（一场会话只剩一套标签）。
话题段是这两者之间唯一说得通的中点。

**为什么段不复制原文。** 曾经考虑过"切出的子文件各自带一份原文"。否决理由很硬：
那就变成了两份真相，purge 穿透、导出一致性、话题交织全部要额外处理。
区间引用零成本，还顺带允许一条消息属于多个段。

**为什么打标单位是会话。** 上下文完整，判定更准；调用次数下降一个数量级
（按消息打标是逐条调用，按会话是逐场调用）。

**为什么闭集 + 待审。** 不闭集，标签会漂移成同义词的坟场；闭集但不留出口，
模型只能倒向"其他"（实测：起步只有 10 个粗类时，16 条里 5 条进"其他"，
而且**一次都没提议新标签**）。所以出口是必须的：**自编值入待审、不进检索、等人批**。
批准是立即可生效的，因为关联在打标时就写好了，过滤的只是 `state`。

**为什么词表必须从真实数据长出来。** 拍脑袋列词表，列出来的是"你以为用户会聊什么"。
实测方法：把消息按批喂给模型"只归类不打标"，再对候选做合并。样本量决定质量——
扫最近 600 条时，主题被最近一场对话占满，没有任何领域词；扫 2500 条，
领域词才出现。**结论：词表质量取决于样本量与合并，不取决于提示词写得多漂亮。**

**为什么情绪只标自述。** 初版提示词下，某一种情绪标签覆盖了近 40% 的段——
抽样一看，模型把"是不是……吗"这种**提问语气**读成了情绪。这是提示词缺陷，不是真实分布。
A/B 对照（20 场、同一词表、只改情绪规则）结果：现行规则 0.78 个/段、目标标签占 50.0%；
"只标自述"规则 0.07 个/段、占 3.3%。采纳后者，并抽检确认它不是"一律不标"
（有真自述被正确标出，有提问语气被正确去掉）。

> 诚实边界：单场波动很大，同一场重打可能给出不同结果。3.3% 是 20 场均值，
> 不是"每场都干净"。

**被否决的方案**

- 扁平标签：维度坍缩。
- 复制出子文件：两份原文。
- 按消息打标：碎片化、成本高一个数量级。
- 让模型做第二次"同义合并"：它会把 is-a 关系当同义吞掉（"市"和"省"被合成一类）。
- 新增"立场"维度（已决定/已放弃/摇摆/支持/反对）：**它自己就是蒸馏**——
  把"断言 + 理由 + 时间 + 边界条件"压成一个词，正是第 1 节第 2 条红线反对的东西。
  态度属于另存的、长期有效、经常更新的用户状态（见第 11 节），不靠打标签得到。
- 只给粗类、不留待审出口：模型倒向"其他"。

**怎么验收**

- `smoke_tag` 第 1–7 项：切段、多维、闭集外入待审、待审不参与检索、段精确映射回消息区间、
  打标过的会话不重复入队。
- `smoke_tag` 第 13 项：标签真的接进对话链路（标签主、全文兜）。
- `tools/eval_emotion.py`：情绪规则的 A/B 对照，可复现；
  `pmem tag rerun --conversation <id>` 用于重打单场（提示词改了能重跑，否则实验无法验证）。

## 10. 复查：只记录，不催改

**结论**

- **每周**：最近 N 天 vs 更早，找前后矛盾的说法（一次调用）。
- **每月**：在**影子库**里删段重打，与真库逐场比对标签集合 → 差异即"漂移"。
- **待裁决清单**：`pending list / answer / propose / apply / reject`。
- `answer` **只记录说明，不改状态**；要关闭必须显式 `resolve`（`dismiss` 表示"不是问题"）。
- **两段式**：你说明之后，系统可以给**一条具体动作**（合并哪两个实体、区间怎么改），
  但 `propose` **只写建议、不改任何记忆**；`apply` 才执行，并写 `action_log`。
- 动作种类是**闭集**（`merge_entity` / `split_entity` / `set_tenure` / `merge_tag` /
  `merge_conversation` / `noop_close`），模型选不出就 `noop_close`。
- 去重用独立列 `sig`；已 `dismissed` 的不再报。
- **一切只记录，不催改**；"什么时候算处理完"由人定。

**理由**

复查的价值不在"发现问题"，在"把只有人能判的那部分挑出来"。所以它对**动作**必须克制：
如果程序会自动关闭、自动合并、自动修正，人就没机会看到"它判错了"。

**为什么只记录不催改。** 用户明确要求：矛盾点和同义合并一样，都不催促修改，
只记录，让他有空时回一句。这条不是礼貌问题，是**人机分工**问题——
一旦程序有"催"的动作，人就被降级成了确认按钮。

**为什么月度对比要在影子库做。** 重整理会覆盖历史结论。在真库上跑一次"重打最近 50 场"，
如果结果不如上一次，历史就被改坏了，而且**无法回滚**。所以月度用 `con.backup()`
复制一份库，在副本里删段重打，只比结果。测试里专门断言"影子库不污染真库（段数不变）"。

**为什么去重要用独立列而不是 `payload LIKE`。** 踩过：`sig` 里嵌 JSON，
存进去时引号会被转义，`LIKE` 匹配不上，于是同一条每次都重报一遍。

**为什么"说明"和"动作"要分两段。** 你说"这是同一个人"，系统可以立刻做三件不同的事：
合并实体、把两个名字记成 alias、或者什么都不做只关掉。**这三种都合理**，取决于你想怎么处理。
一步到位的写法只能二选一：要么听完就猜着改（改错了还得靠你发现），要么永远不改（
那 4 条待裁决会一直躺着）。两段式把"我打算怎么改"先摆出来给你看，再执行——
它把不可逆的写入变成了一次**可审阅的提议**。

`propose` 只写一列（`proposal`），`apply` 才动数据，而且动之前**再校验一次**：
提议之后数据可能已经变了（别处的对话删了那个实体），旧提议照执行会改错东西。
执行包在一个事务里，失败整条回滚——**不做半拉子修改**；成功则写 `action_log`，
记下"谁、何时、执行了哪个动作、结果是什么"。

**被否决的方案**

- 自动关闭 / 自动合并：人失去看到"判错"的机会。
- 听完说明就直接改（一步到位）：改错了只能靠人发现，且不可逆；也解释不了"它为什么这么改"。
- 在真库上重打做对比：不可回滚。
- `payload LIKE` 去重：转义后匹配不到。
- 把"每月"做成自动定时任务并强制出报告：变成催办。

**怎么验收**

- `smoke_review` 12 项：回答只记录不自动关闭、关闭后从 open 列表消失、每月复查能记下漂移、
  影子库不污染真库（段数 1→1）、去重不重复报。

## 11. 实体与用户状态：双轨，且都指向原文

**结论**

**实体层**：`entities(id, kind, name, is_role, aliases)` + `entity_mentions(segment_id, entity_id)`
+ `entity_tenure(entity_id, org_id, valid_from, valid_to, evidence, origin, basis)`。

- `kind` = `person` / `org`；`is_role=1` 表示"老板""猎头"这类**角色**（不是自然人）。
- 时间区间**未知就留 `NULL`**，不假装知道。
- `evidence` 存消息 id；`basis` 存**原话片段**（v14 补的，只有 id 人看不出所以然）。
- `candidates --when …` **只返回候选、不下结论**。

**用户状态**：`profile_facts(kind, subject, value, valid_from, valid_to, evidence, origin, superseded_by)`。

- 一条状态 = 断言 + 有效期 + 证据 + 确认方式，**不是摘要结论**。
- `origin`：`derived`（机器推断）/ `confirmed`（用户确认）。
- **推断永远不能覆盖已确认**；冲突时两条并存，交人。
- **旧值不删**，用 `superseded_by` 串起来。
- 自动推断（如任职经历）**只写 `derived`**，无证据的直接丢弃。

**理由**

这是"机器能定"与"只有人能定"的边界。

**为什么需要实体层。** 有些问题机器判断不了，而且不是"算力不够"，是**信息不在库里**：
"半年前吐槽的那个老板"和"昨天吐槽的前司老板"是不是同一个人？
吐槽这件事**没有自己的时间戳**，库里只有"产生对话的时间戳"。
即使能从原文推出"中间换过工作"，得到的也只是"跨了雇主"，不是"是不是同一个自然人"。
所以系统能做的只有两件事：把归属区间算出来（可推断），把同一性问题挂进队列（要人答）。

**为什么"只给候选"。** 角色词会被高频提及（一个"老板"可能横跨几十段），
任何自动归并都会错，而且错得安静。候选 + 原文 + 时间区间，交给人一句话就能定。

**为什么双轨。** 自动推断会错，而且复核的人也会错——踩过一次：把一条真实任职判成"存疑"，
理由是拿另一段更早的经历去套。**一个人的经历里可以有多段，不能用一段否定另一段。**
既然机器和人都可能错，就不该只留一个值：`derived` 可被新证据推翻，`confirmed` 不动，
冲突时并存。这样"谁在什么时候基于什么改了口"始终可查。

**为什么文件只导出、不反向写库。** 表是真相，文件是视图
（`pmem profile export` 生成 `data/profile/<kind>.md`，只读表、只写文件）。
文件若能动，就出现了第二个事实来源，与"原文唯一"直接打架；现在它随时可以重新生成，
删了也不心疼。导出只取**当前有效**的行（`superseded_by IS NULL`）——被取代的旧值留在表里，
要看"什么时候变的"用 `pmem profile history`，不往人读文件里堆。

**被否决的方案**

- 把推断直接写成事实字段：推断链丢失，且无法区分"他说的"和"我猜的"。
- 自动归并角色实体：错得安静。
- `derived` 覆盖 `confirmed`：用户的确认会被机器悄悄推翻。
- 用 `DELETE` 清理旧值：回答不了"我以前怎么想、什么时候变的"。
- 用标签承载"态度"（第 9 节的"立场"维度）：那是蒸馏。
- 把"文本矛盾"当主战场：人自己读一遍就看得出冲突，机器再报一遍是多余动作。

**怎么验收**

- `smoke_entity` 8 项：区间覆盖（昨天 → 已不在）、换过老板时给多候选、
  无归属的频繁角色进待确认、不动原文（消息数/段数不变）。
- `smoke_profile` 6 项：推断不得覆盖已确认、旧值不删且被串起来、`list` 只显示当前有效、
  实体问题进队列且幂等。
- `smoke_infer` 6 项：无证据的推断被丢弃、重复跑不叠加、确认后不被推断覆盖、原话依据落库。

## 12. 接入：两个出口，一个入口

**结论**

运行时（任何 agent、IM 机器人、桌面应用）**只调两条命令**：

- `pmem context "<用户这句话>"` → 返回一份自包含的 `messages`（system / hot / hits / user），
  以及路由与门的元信息。**不生成、不写消息。**
- `pmem note "<一条消息>"` → 写消息（可带附件），**时间由 pmem 盖章**。

补充约定：

- `source` + `session` 让 IM 的外部会话稳定落成一场 pmem 会话（跨天续聊不断开）。
- `note --attach <路径>`（可多次）是 IM 收图/收文件的入口：sha256 落盘、挂到消息上。
- 上下文的决定权 **100% 在 pmem**；运行时不许有自己的历史来源。
- **人设与语气也在 pmem 这一侧**：`persona.md`（gitignore）拼在系统提示词最前面，
  运行时不需要、也不应该自己加一段"你是一个……"。

**理由**

把"该带什么上下文"收进一个出口，是为了让记忆行为**可测**。如果运行时可以自己拼上下文，
那么"为什么模型这次记得、那次不记得"就永远说不清，测试也只能测片段。

**为什么人设必须放在 pmem 里，而不是让运行时自己加。** 三个理由：

1. **它是上下文的一部分**，和"注入哪些记忆"是同一条流水线。运行时再拼一段，
   就出现了两处 system 提示词互相打架——一个说"简短"，一个说"详细列出"，模型只能随机挑。
2. **它必须能被单独关掉和替换**。语气是偏好，不是规则：改 `persona.md` 立刻生效，
   删掉文件就退回内置的克制语气，不用重启、不用改代码。
3. **它不能覆盖记忆红线**。人设里写"你什么都知道"也不会生效——提示词里把记忆规则放在人设之后，
   并明写"人设不许覆盖记忆规则"。语气可以个人化，事实边界不行。

代价是 pmem 需要知道"这个人想被怎么称呼、讨厌什么腔调"，这属于个人数据，
所以文件进 `.gitignore`，仓库里只留一份 `persona.example.md` 供参考。

**为什么是两个出口而不是一个。** 生成在运行时那一侧（模型、温度、流式、工具都在那边），
记忆在这一侧。`context` 只读、`note` 只写，职责不重叠——这样"只读接口"可以被单独验证，
"写入必然盖章"也可以被单独验证。

**为什么精确地说"不写消息"而不是"只读"。** 诚实的附注：`context` 会 upsert 一条
"实时对话 <日期>"的会话行（首次调用时），但**不写任何消息**。
"只读接口"这个说法要精确成"不写消息"，否则文档在撒谎。

**为什么不做可插拔的抽象接口/预留插件位。** 两条命令就是最小公约数：
任何会调命令行的程序都是合法接入方。预留要先猜对方形态，猜错就返工；
执行器中立不需要猜。同理，任务对象只记录"存在/状态/产出/归属"，`executor` 只是字符串，
任何进程都可通过 `task start|log|finish` 当执行器，**不需要改 pmem 一行代码**。

**被否决的方案**

- 自建 transport（在核心库里写某个 IM 平台的协议）：耦合且无法复用。
- 预留插件接口 / 抽象基类：猜形态，猜错返工。
- 让运行时自己拼上下文或自带历史：记忆行为不可测。
- 运行时传时间戳：见第 4 节。
- 对话中途同步做切段打标：一轮对话要等 N 次调用。

**怎么验收**

`smoke_ports` 16 项，**全部跨进程**（走命令行、重定向到文件、不开管道）：
重定向输出必须是合法 UTF-8 JSON、`messages` 自包含且末条就是用户这句话、
`note` 拒绝调用方传时间、盖章后下一轮 `context` 能在热窗看到、默认不调用的会话不漏进上下文
（并有反向对照证明不是空测）、查不到时 `hits_text` 为空、上下文在预算内。

> 为什么必须跨进程：函数级 `import` 调用会**绕过命令行边界**，
> 而编码、参数契约、退出码、只读性这些问题只在该边界上出现。

## 13. 测试策略：行为断言，不是覆盖率

**结论**

验收是一组**跨层行为断言**，共 **95 项 / 9 个套件**（`verify` 9 + 8 个 smoke 共 86），
入口是一条命令：`python tools\run_all.py`。断言的四条原则：

1. **测行为，不测实现分支**。断言写"滑出热窗后必须能检索到，且不重复"，不写"调用了哪个函数"。
2. **必须带反向对照**。证明"这条测试不是空测"——例如静音会话：不触发词时不能进上下文，
   **但点到触发词时必须以同一条断言证明它能进**。
3. **用临时库**。任何会写库的断言都建在临时库上，绝不碰真实记忆。
4. **断言条数写死**。每个套件的期望条数硬编码在 `run_all.py` 里；条数对不上也算失败。
   理由见"理由"最后一段——这是唯一能防住"断言被删掉、脚本仍然打印全部通过"的办法。

**理由**

这些测试不是"代码覆盖率"，而是**行为不变量的清单**。项目里最难发现的 bug，
并不是某个函数算错了，而是**跨层那一步没人守**：曾经真的发生过——
打标做了全库、词表也批了几百个，但对话时**一条标签都没用上**，
因为测试只测了"能按标签查"，没测"对话时会不会用标签"。没有任何红灯。

反向对照解决的是另一个失效模式：一条断言可能因为"整个功能没接线"而恒真。
"静音会话不进上下文"在功能完全没实现时也是真的——所以必须有另一半：
点到触发词它就得进。

临时库则保证"跑测试"这个动作本身是安全的。测量不该改变被测对象。

**为什么要把断言条数写死。** "打印全部通过"这件事本身可以是假的：删掉一条断言，
剩下的照样通过；整个跳过某个套件，也照样通过。所以 `run_all.py` 多做两件事——
核对每项的 `[PASS]` 条数是否等于期望值，以及把"**没有任何输出**"也判为失败。
这不是洁癖，是有原型的：`tools/smoke_http.py` 没有断言、要先起一个假模型服务，
服务没起时退出码是 -1。它一旦被当成"验收项"塞进自动跑，就会稳定贡献一个假绿灯。
（它现在不在 `run_all.py` 里，见下面的被否决项。）

**被否决的方案**

- 只用 `verify` 当验收：它测的是存储层与索引层，跨层完全测不到。
- 只 `import` 函数做单元测试：绕过命令行边界，编码/参数/退出码问题全部漏掉。
- 用真实库跑断言：测量污染被测对象。
- 不带反向对照：断言恒真的情况无法区分"功能正常"和"功能不存在"。
- 用通配符把 `tools/smoke_*.py` 全跑一遍当验收：手动联调脚本（无断言、依赖外部服务）
  会混进来，于是"全部通过"变成一句没有内容的话。

**怎么验收**（就是它们自己）

| 命令 | 项数 | 守的是什么 |
|---|---|---|
| **`python tools\run_all.py`** | **95** | 下面 9 条的总入口，外加**断言条数校验**（少一条、多一条、无输出都算失败） |
| `run.cmd verify` | 9 | FTS、中文精确子串、查不到返空、sha256、导出往返、时间精度、证据门、purge 四层、Git 防误提交 |
| `python tools\smoke_task.py` | 8 | 任务对象、执行器中立、热窗排除任务过程、`context` 不写消息、`note` 盖章 |
| `python tools\smoke_tag.py` | 22 | 切段、多维、闭集/待审、is-a 查父含子、静音、热窗边界、不重不漏、标签接入链路、转冷入队与**自动整理**、反问 |
| `python tools\smoke_ports.py` | 16 | 跨进程两个出口、UTF-8、自包含 messages、盖章、热窗延续、静音反向对照、IM 落点与收图 |
| `python tools\smoke_review.py` | 12 | 只记录不催改、去重、影子库不污染真库；两段式（提议不动数据 / apply 才合并 / 状态机 / 审计） |
| `python tools\smoke_entity.py` | 8 | 归属区间、多候选、待确认、不动原文 |
| `python tools\smoke_profile.py` | 7 | derived 不覆盖 confirmed、旧值不删、幂等入队 |
| `python tools\smoke_images.py` | 7 | 单张失败不中断、离线不写假描述、描述不替代原文；热窗标注带图/未描述 |
| `python tools\smoke_infer.py` | 6 | 无证据丢弃、去重、确认优先、依据落库 |

**改完必须全跑。** 少跑一条，就等于没有基线。

## 14. 被否决的方案（汇总）

一条一句，方便快速否决"我们是不是该试试……"。

| 方案 | 否决理由 |
|---|---|
| 向量检索 / 语义近邻召回 | 近邻不等于事实；无时间轴；不可读、不可迁移、不可审计 |
| 向量 + FTS 双路 RRF 融合 | 融合权重说不清，会把"语义相近但事实无关"抬回来 |
| 向量只用于重排候选 | 把不可解释的分数引入最后一公里 |
| 用摘要/条目替代原文 | 一次性销毁可追溯性；偏好被压成断言，理由与边界全丢 |
| 让模型推断时间戳 | 推断值与真实值同形，之后无从区分 |
| `unknown` 填占位时间 | 比缺失更坏：混进排序、热窗与衰减，且再也挑不出来 |
| 用导出时刻当发生时刻 | 时间轴倒挂 |
| 用系统时区/`zoneinfo` 转换 | 机器间不一致；引入 `tzdata` 依赖，破坏零依赖 |
| 附件按消息 id 命名 | 同一张图存多份，purge 易漏副本 |
| 物理删除行 / 纯软删 | 前者破坏 append-only 与级联；后者是"看不见"不是"删掉" |
| trigram / unicode61 直接上 | 实测对两字中文词返回 0 条 |
| 多关键词 AND | 现实里一条都不剩 |
| 取完再过滤（当前会话/静音/热窗） | 名额被污染，真实历史被挤出 |
| SQL `exp()` 做时间衰减 | 依赖编译开关，换机器就没了 |
| 扁平标签 | 维度坍缩，必然长出"其他"垃圾抽屉 |
| 切段时复制原文 | 两份真相：purge、导出、交织全要额外处理 |
| 按消息打标 | 碎片化且成本高一个数量级 |
| 让模型做二次同义合并 | 会把 is-a 吞成同义（省 / 市被合成一类） |
| "立场"维度 | 它自己就是蒸馏，违反"原文全量"的精神 |
| 词表式触发第三档复核 | 留出样本仅 66.7% |
| agent 自主决定是否检索 | 对照实测 0.50 准确率、漏查 0.60 |
| 信任模型给出的关键词 | 会从最近对话搬词，造成过度联想 |
| 提示词约束证据门 | 模型会把话圆回来 |
| 证据不足时只陈述、不追问 | 用户明确否决；把问题丢回去还不给线索 |
| "跨自然日"判睡眠边界 | 熬夜场景双向失效（没睡算睡了、睡了算没睡） |
| 热记忆静默截断最旧几条 | 制造不可感知的失忆 |
| 注入与排除分别算边界 | 产生"既没注入又查不到"的永久黑洞 |
| 复查自动关闭/自动合并 | 人失去看到"判错"的机会，被降级成确认按钮 |
| 在真库上重打做月度对比 | 不可回滚，历史结论被改坏 |
| 用 `payload LIKE` 做待裁决去重 | JSON 转义后匹配不到 |
| 自动归并角色实体 | 高频角色词跨几十段，错得安静 |
| `derived` 覆盖 `confirmed` | 用户的确认被机器悄悄推翻 |
| 用 `DELETE` 清理过期状态 | 回答不了"什么时候变的" |
| 从 `profile/*.md` 反向写库 | 出现第二个事实来源，与"原文唯一"打架 |
| 核心库内自建 IM transport | 耦合、不可复用；transport 属于运行时那一侧 |
| 预留插件接口 / 抽象基类 | 猜形态，猜错返工；命令中立已经够用 |
| 任务队列 / 优先级 / 重试调度 | 队列是调度逻辑不是数据类型；加列或加外部进程即可 |
| 同步做切段打标 | 一轮对话要等 N 次模型调用 |
| 只用 `verify` 当验收 | 跨层那一步完全测不到，出过真实事故 |

## 15. 从空库到能查（最短上手顺序）

一条路走到"能检索 + 能对话"，每步都有可验证的产物。

```bat
:: 1. 建库（空库，schema v15）
run.cmd init
run.cmd verify                     :: 空库时 7 项通过 + 2 项跳过（无探针/无附件），是正常基线

:: 2. 导入（中立导入格式 + 适配器；Takeout 或 Voyager）
run.cmd import takeout D:\path\to\takeout-xxx.zip
run.cmd stats                      :: 看清场次/消息/附件/时间精度分布
run.cmd gaps                       :: 缺口是一等公民，不是一行警告

:: 3. 起步词表（闭集必须先有内容，否则标签无从选）
run.cmd tag seed
run.cmd tag propose --limit 2500   :: 从真实消息里提议候选（样本量决定质量，见第 9 节）
:: 审候选 → run.cmd tag add --dim 主题 "某个具体主题"
:: 自编值此时仍在 pending，不进检索

:: 4. 打标（按会话切段 + 多维；闲时跑）
run.cmd tag run --pending
run.cmd tag list --state pending   :: 待审的看一眼；approve / reject 由人定
run.cmd entity sync                :: 把已批准的 人物/机构 投影成实体

:: 5. 检索（两条路都验一遍）
run.cmd search 某个型号或编号        :: 全文兜底
run.cmd search --tag 某个地点        :: 标签主路径；默认含子级，--exact 关掉
run.cmd hot                        :: 看当前清醒段装了什么

:: 6. 接入（运行时只调这两条）
run.cmd context "用户这句话"        :: 返回自包含 messages，不写消息
run.cmd note "用户这句话" --attach D:\path\to\image.png
```

之后日常只有三条命令：`context` / `note` / 夜里 `tag run --pending`。
复查与待裁决是**人主动看**的，不是系统推送的：

```bat
run.cmd review weekly
run.cmd review monthly
run.cmd pending list
```

> 上手时最容易踩的三个点：
> ① 解释器要 **3.11+**（`tomllib`），系统自带的 3.9 不够，`run.cmd` 会自动挑；
> ② Windows 中文终端是 GBK，输出被重定向时 `cli._setup_console()` 会切 UTF-8——
> 所以 `run.cmd` 必须保持**纯 ASCII**，否则中文注释会被当成命令执行；
> ③ 不要用 PowerShell 的 `Set-Content -Encoding UTF8` 改这些 UTF-8 源文件，
> 它会把文件读成 GBK 再写回，中文全毁（本项目被这样毁过一次）。

## 附：这份文件怎么维护

1. **一条决策 = 四段**。结论、理由、否决项、验收。写不出"被否决的方案"，说明还没比较过。
2. **数字必须能重跑**。给命令、给 `文件:行`、给表行数。给不出依据的，写"未验证"，
   不要写成结论。
3. **不要写真实数据**。例子一律一般化；具体数字、真实原话、真实实体留在私有证据目录。
4. **代码与本文不一致时以代码为准**，然后改本文——反过来（改代码去迁就旧文档）
   在本项目里已经出过事。
